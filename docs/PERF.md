# 性能实测

合同里有两条时间指标：

- 单次完整检查 **≤ 30 分钟**
- 报告输出 **≤ 1 分钟**

这份文档记录的是**实测值**，不是估计值。

---

## 一、解析（起 NX + 读几何）

用同一份零件复制成不同规模装配来测，两次都是 `--no-cache`：

| 规模 | 面 | 边 | 耗时 |
|---|---|---|---|
| 6 组件 | 78 | 114 | 32.2 s |
| 24 组件 | 312 | 456 | 33.5 s |

拆开看：

```
固定开销（NX 启动 + 打开文件 + 关文件）  ≈ 31 s
面相关开销                              ≈ 5.6 ms / 面
```

**3000 个面的模型**大约是 `31 + 3000 × 0.0056 ≈ 48 s`，离 30 分钟很远。

固定开销占九成，所以「解析一次、44 个检查项共用」这个设计是有效的——
如果每个检查项都重新起一次 NX，光启动就要 44 × 31 s ≈ 23 分钟。

---

## 二、检查（纯 Python，不碰 NX）

同一份机器上：

| 规模 | 检查项 | 耗时 |
|---|---|---|
| 78 面 / 6 组件 | DFM-02、DFM-31、DFM-32 | 0.25 s |
| 312 面 / 24 组件 | 同上 | 0.28 s |

其中约 0.2 s 是 Python 启动。检查逻辑本身是毫秒级。

24 组件场景跑出 72 条 DFM-31（24 × 3 个非标孔），用的还是 O(n²) 的两两配对——
组件数再多也扛得住。

---

## 三、还缺什么

**没有测过真正的「大模型」**。上面用的是同一份 13 面的零件复制 24 份，
不是单个 3000 面的复杂零件。两者的差别在于：

- 复杂零件的**面类型更杂**（B 曲面多），`GetFaceProperties` 单次更慢；
- 复杂零件的**邻接关系更密**，邻接对数量增长更快；
- 装配层级更深时，组件展开的开销也会上升。

要真正验证「30 分钟」这条指标，需要一个真实的大模型。这是启动会要甲方的东西之一：
**给一个面数量在 1000 以上的真实产品模型**。

在此之前，能说的是：现有实测的规模代价是 5.6 ms/面，固定开销 31 s，余量很大。

---

## 四、测量口径

```powershell
# 解析计时要加 --no-cache，否则会走缓存，测出来是 0
python -m nxdrp extract 模型.prt -o out.json --no-cache

# 检查计时
Measure-Command { python -m nxdrp check out.json -r rules/dfm_default.json -o f.json }
```

注意：`extract` 的输出里 `耗时` 那一行是 journal 内部自测的，与外部 `Measure-Command`
可能差 1~2 秒（进程启动开销），两者都算合理。
